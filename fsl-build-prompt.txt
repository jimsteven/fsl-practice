Personal Filipino Sign Language Learning App Build Prompt

Act as a senior product engineer, accessible interface designer, and machine-learning engineer. Build a usable, polished personal Filipino Sign Language learning and recognition web app for my own practice. Present it consistently as a personal project in the interface, documentation, and handoff. Start with a working practice experience and real camera/hand tracking. Never present a mockup as working recognition.

Project brief and implementation boundaries

Track every decision as PROJECT REQUIREMENT, PROPOSED IMPLEMENTATION, or UNRESOLVED INPUT. Treat the technical scope below as the project brief; distinguish it from the suggested implementation choices and safeguards. Trained FSL weights, an approved dataset, reference media, and measured results have not been supplied. Do not pretend these assets or evidence already exist.

1 Project requirements

Purpose: a personal FSL practice and learning app, NOT a full-sentence translator. Prioritize a beginner/intermediate learner's daily practice. Retain learner and teacher-facing experiences for authorized guidance, and design respectfully for the Deaf and hard-of-hearing community.

Content:
- Complete FSL alphabet; exact authoritative inventory requires confirmation.
- Numbers 0–9.
- Approximately 20–30 expert-selected everyday words/phrases, including greetings, directions, and health/emergency vocabulary. Do not invent an approved list.
- Static letter/number and dynamic word/phrase recognition. Confirm each sign's actual motion/capture requirements with an FSL expert.
- Expert-checked videos, images, and landmark references.

Functions:
- Real-time webcam input, MediaPipe's 21 landmarks per detected hand, and deep-learning classification.
- Immediate predictions; quantitative assessment and improvement feedback concerning handshape, position, and movement trajectory where validated.
- Repeated practice and progress tracking.
- Storage of references, sessions, recognition results, and progress.

Explicit stack: React, HTML/CSS/JavaScript; Python and OpenCV preprocessing; MediaPipe Hand Landmarker; TensorFlow/Keras training; TensorFlow.js browser inference; Firebase Authentication, Firestore, and Hosting. Plan for CNN classification; LSTM is a potential addition for temporal recognition, not a settled requirement. Resolve the model/input design against the actual dataset before training. Figma/diagrams.net are optional; Raspberry Pi is a feasibility consideration, not a hardware deliverable.

Targets: responsive Chrome/Edge laptop, Android Chrome, and iPhone Safari. Camera, adequate compute, lighting, and an uncluttered view matter. Initial internet is needed for model downloads; offline operation is possible, not committed.

Quality checks: recognition accuracy, latency, usefulness, user satisfaction, and ISO 9126 quality categories as a development checklist. Do not claim certification or invent results.

Limits: no ASL/BSL substitution, comprehensive regional coverage, full-sentence translation, or facial/body-expression interpretation. This supplements rather than replaces interpreters or formal instruction. Document dataset diversity and the limits of available validation; do not promise proven learning outcomes or long-term retention.

2 Honest operating modes

Implement the scaffold without waiting for training assets, but never use random predictions, fabricated scores, generic ASL weights, or hardcoded success messages.

- Tracking only: actual camera/landmarks work; show “Hand tracking is available. FSL recognition is not configured.” No sign prediction, correctness percentage, or model-derived correction.
- Validated recognition: enable only for compatible FSL weights, labels, preprocessing, provenance, and validated supported signs.
- Demo: isolated synthetic fixtures may illustrate teacher/progress screens. Label them clearly and never mix them into real records or measured results.

Missing/unapproved reference media must show an unavailable/review-pending state. Do not substitute generated signing hands, invented FSL instructions, or unrelated stock media. Expose the approved subset honestly.

4 Interface direction and proposed workflow

Create an intentional educational workspace, not a marketing landing page or generic SaaS dashboard. Make reference hands and live camera dominant. Use thoughtful typography, consistent spacing, comfortable widths, restrained borders, and one modest accent family. Warm neutrals with muted teal are a proposed starting point, not mandated branding.

Avoid purple-gradient heroes, gratuitous glassmorphism, decorative blobs, excessive cards, fake KPI counters/testimonials, meaningless badges, and charts without data. Polish through useful composition, concise copy, and complete states. Use respectful language and expert-reviewed instruction.

Flow: choose supported sign → inspect approved reference → explicitly start camera → practice in the visibly identified mode → receive supported feedback → retry → review/save allowed progress.

Screens:
- Learn: alphabet, numbers, and everyday categories; beginner/intermediate navigation; content/model availability.
- Sign detail: reference media, text context, attribution, reviewed handedness/mirroring guidance, Practice action.
- Practice: large reference/camera areas, start/stop, reference replay and supported speed control, optional landmark overlay, capture/reset, status, feedback, retry.
- Summary/progress: actual attempts/history and well-defined available metrics; honest empty states.
- Teacher: synthetic demonstration initially, then only authorized learner summaries. No unrequested messaging, public leaderboards, or complex school administration.
- Privacy/settings: camera explanation, account/history behavior, available data controls, accessibility preferences.

Desktop: deliberate side-by-side reference/camera layout. Mobile: preserve signing area/aspect ratio, reachable controls, portrait/landscape behavior, and safe areas without horizontal scrolling or cropping hands for aesthetics.

Target WCAG 2.2 AA with semantic HTML, keyboard access, visible focus, contrast, readable sizing, touch targets, zoom/reflow, reduced motion, captions for spoken reference audio, and meaningful text context. Never rely only on sound, color, or gestures. Announce important states without screen-reader updates every frame. References remain browsable without camera access.

5 Architecture and camera implementation

Inspect existing repository instructions/conventions first. For an empty project, use a simple React setup with a lightweight build tool; TypeScript is optional and a proposed choice. Minimize dependencies, verify current official documentation, pin versions, and keep lockfiles.

Separate content, camera lifecycle, tracking/normalization, model adapters, feedback rules, session state, persistence/auth, and UI. Keep Python/OpenCV/TensorFlow training offline; use TensorFlow.js browser inference. Do not add server camera streaming.

Use Firebase emulators or clearly labeled local adapters when credentials are absent. Never fake cloud saves or deploy permissive rules. Do not provision paid services or publish/deploy without explicit authorization.

Camera requirements:
- Explicit start action, clear purpose, no microphone request; explain secure-context and permission requirements.
- Handle denied/missing camera, loading, no hands, occlusion, unsupported device, model failure, and connection errors.
- Stop tracks on Stop, navigation, and teardown. Prevent duplicate streams/loops; pause unnecessary inactive processing.
- Keep frames/transient landmarks in memory by default.
- Use actual 21-point MediaPipe output for each required detected hand. Handle handedness, missing hands, mirroring, resize, rotation, and aligned video/overlay/model coordinates.
- Bound frame scheduling and inference queues; measure responsiveness and use workers where appropriate.
- For dynamic signs, specify capture boundaries, timestamps, sequence length, resampling/padding, and missing-frame behavior from the actual training contract. Explicit Start/Stop capture is a proposed initial UI, not a sequence classifier.
- Fail closed to tracking-only if the model is missing/incompatible. Distinguish tracking failure, unsupported sign, uncertain/unknown result, and supported prediction.

6 Model and feedback integrity

Define a versioned model manifest: supported sign IDs, lexicon version, model/provenance, task type, input/output shapes, preprocessing, handedness, temporal requirements, and confidence/calibration policy. Validate compatibility; never guess class order.

Training needs approved labeled data, rights, consent, and expert review. Provide reproducible scaffolding and export instructions if data/weights are missing, but never call unrun code trained. Use signer-disjoint held-out evaluation and prevent signer/clip/frame leakage. Document diversity and capture conditions without inferring sensitive demographics from video. Report per-class metrics, confusion, and unknown-sign behavior, separating static and temporal tasks. Calibrate thresholds on held-out data rather than inventing a convenient cutoff.

Keep tracking quality, model confidence, measured recognition accuracy, and pedagogical correctness distinct. Confidence is NOT “how accurately you signed.” Handshape/position/trajectory scores need defined normalization, expert-approved tolerances, and validation. Otherwise display “Detailed correction unavailable.” Basic observable framing guidance is allowed when supported, but not invented finger-level advice or mastery percentages.

7 Data access and privacy

Propose minimal versioned schemas for approved sign references/media rights; owner-scoped sessions; recognition/abstention results with model versions and score definitions; derived progress; and trusted teacher assignments. Final roles, guest persistence, history, and retention are unresolved. Default to ephemeral local tracking and no real teacher access until approved.

Use deny-by-default Firestore rules. Validate ownership/allowed fields, prevent ownership/role tampering, and restrict teachers to verified assignments established through a trusted authorization path. Learners cannot self-grant teacher/admin roles. Client-side button hiding is not authorization.

No default storage/upload of video, screenshots, audio, or continuous landmark histories; landmarks are not automatically anonymous. No cloud camera inference, advertising, session replay, or third-party analytics without separate review/authorization. Do not log sensitive data or credentials. Keep secrets/service-account keys out of clients and repositories; Firebase client configuration is not an authorization mechanism.

Explain actual on-device versus saved data behavior. Establish retention/deletion and implement approved controls before real learner-history collection. Do not claim legal compliance from this prompt.

Use synthetic development/test data. If the app is later used by children, do not collect identifiable child data until appropriate consent/assent, guardian permission where applicable, access restrictions, and retention/deletion are established. Any school use also requires the responsible institution's approval. Separate optional recording or dataset contributions from ordinary practice and obtain specific authorization. Personal-project status does not remove privacy obligations.

8 Stages and verification

Stage 1: working responsive navigation, content schemas/unavailable states, camera start/stop, real landmarks, tracking-only mode, local sessions, and clearly labeled teacher/progress demos. A learner can use the tracking flow without fake recognition.

Stage 2: authentication/persistence, tested owner-scoped rules, approved role/history behavior, and privacy controls using emulators or an authorized project. Keep collection of other people's personal data gated by the required permissions.

Stage 3: approved media and compatible validated FSL models, supported static/temporal inference, abstention, measured latency, and validated feedback only. Missing model/data/rubric blocks these capabilities, not the safe scaffold.

Stage 4: functional, accessibility, security/privacy, device/browser, and model evaluation. Report actual evidence and limitations. Offline/PWA support is optional only after scope, caching/privacy, and behavior are approved/tested.

Tests:
- Build/type checks where applicable, linting, unit/component tests.
- Camera denial, start/stop/restart, navigation cleanup, duplicate loops, coordinate transforms, missing/incompatible models, and abstention.
- Temporal preprocessing when implemented; correct progress aggregation and demo/real separation.
- Emulator rejection of unauthenticated, cross-user, owner-tampering, role-escalation, and unauthorized-teacher requests.
- Keyboard, accessible status, automated accessibility checks plus manual review.
- Network inspection confirming no default camera-frame/landmark uploads.
- Rendered mobile/tablet/laptop layouts, zoom, focus, empty/error/loading states, rotation, and signing visibility.

Test actual available target browsers/devices and list untested ones; desktop emulation does not prove iPhone camera compatibility. Measure tracking, inference, and end-to-end delay separately with device/browser/model/coverage context. Accuracy/FPS/latency thresholds remain unresolved; label proposed budgets. Never fabricate test results or user feedback.
